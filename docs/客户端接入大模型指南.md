# 客户端应用大模型接入指南

> 本文档说明移动客户端（Android/Kotlin）如何接入大语言模型（LLM），覆盖架构选型、流式输出、会话管理、安全与成本控制。API 示例以 Claude（Anthropic）为参考，其他厂商（OpenAI、Gemini 等）的接入思路一致。

---

## 一、三种接入架构

客户端应用大模型有三种主流架构，选型是第一个要做的决定：

| 架构 | 说明 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **A. 后端代理**（推荐 ✅） | 客户端 → 自建后端 → LLM API | API Key 不出服务器；可做鉴权、限流、审计、计费 | 需要维护后端服务 | 正式产品 |
| **B. 客户端直连** | 客户端 → LLM API | 无后端、链路短、上手快 | **API Key 打包进 APK，可被反编译提取**；无法控制用量 | 原型验证、个人实验 |
| **C. 端侧小模型** | 模型直接跑在设备上（本地推理，如 MNN-LLM / llama.cpp，详见 1.1/1.2 节） | 离线可用、零 API 成本、隐私好 | 能力有限、耗电、包体积大 | 输入法联想、离线摘要等轻量任务 |

**结论：正式产品一律走架构 A。** 架构 B 仅用于开发调试；架构 C 与云端模型互补，不替代。

### 1.1 端侧推理架构 C 详解

端侧小模型 = **端侧本地推理**：模型文件打包进 App（或首次启动时下载），推理计算完全在手机 CPU/GPU/NPU 上执行，不发出任何网络请求。

与云端方案的本质区别：

| 维度 | 云端 API | 端侧推理 |
|------|----------|----------|
| 网络依赖 | 必须在线 | 完全离线 |
| 延迟 | 300ms~数秒（网络往返） | 首 token 数百 ms，解码 5~30 token/s |
| 成本 | 按 token 计费 | 免费，但耗电、占内存 |
| 隐私 | 数据出设备 | **数据不出设备**（隐私合规利器） |
| 能力 | 旗舰模型，最强 | 1B~3B 为主，能力有限 |
| 模型更新 | 服务端随时升级 | 跟 App 版本走，包体积压力大 |

端侧跑 LLM 的现实约束：

1. **模型大小**：必须量化，4-bit（Q4）是主流。经验值：1.5B @Q4 ≈ 1GB 内存（中端机可跑）；3B @Q4 ≈ 2GB（旗舰机流畅）；7B @Q4 ≈ 4GB（大部分手机吃不消）
2. **实际可用模型**：Qwen2.5/Qwen3-1.5B/3B、Gemma 2B、MiniCPM、Phi-3-mini 这个量级
3. **速度**：CPU 解码约 5~20 token/s（取决于 SoC 和模型大小）；上 NPU 可翻几倍，但要用芯片厂商 SDK，碎片化严重
4. **适用场景**：输入法联想、离线摘要、隐私敏感的本地文档问答、弱网兜底——而非通用聊天助手

### 1.2 端侧推理框架对比（MNN / NCNN / TFLite / ONNX Runtime / llama.cpp）

五个框架分两个阵营：**通用端侧推理框架**（MNN、NCNN、TFLite、ONNX Runtime Mobile，主打 CNN/视觉模型）和 **LLM 专用推理**（llama.cpp）。

| 维度 | MNN | NCNN | TensorFlow Lite | ONNX Runtime Mobile | llama.cpp |
|------|-----|------|-----------------|---------------------|-----------|
| **出品方** | 阿里 | 腾讯 | Google | 微软 | 社区（ggml） |
| **定位** | 移动端通用推理 | 移动端 CPU 推理（视觉） | 端侧通用推理（官方标准） | 跨平台通用推理 | 纯 LLM 推理 |
| **LLM 支持** | ✅ 强（MNN-LLM 引擎，Qwen 官方支持） | ⚠️ 弱（非主战场） | ⚠️ 有限（MediaPipe GenAI 路线） | ⚠️ 有限（不算主流选择） | ✅ 事实标准，模型生态最全 |
| **模型格式** | MNN 自有 | NCNN 自有（.param/.bin） | .tflite / .task | ONNX | GGUF |
| **模型来源** | 各框架转换器（PyTorch/ONNX 转换） | 同左 | TF 生态最顺，PyTorch 需转换 | PyTorch 导出 ONNX 很顺 | HF 上现成 GGUF 直接下载 |
| **CPU 优化** | ARM NEON，四核并行 | **业界标杆**，包体最小 | 好 | 好 | 好（ARM/x86 全覆盖） |
| **GPU 加速** | ✅ Vulkan/OpenCL | ✅ Vulkan（稳定）/OpenCL | ✅ GPU delegate | ✅ | ✅ Vulkan/Metal |
| **NPU 加速** | ✅（高通/联发科） | ⚠️ 较弱 | ✅ NNAPI/NN delegate，**NPU 生态最好** | ✅ NNAPI | ❌ 基本无（硬伤） |
| **包体积** | ~1-2MB | **最小（~1MB 内）** | ~1-3MB | ~2-5MB | ~2MB + 模型另算 |
| **iOS 支持** | ✅ | ✅ | ✅ | ✅ | ✅（Metal） |
| **中文资料** | ✅ 丰富 | ✅ 丰富 | ✅ 最丰富 | 一般 | 英文为主 |

其他常见端侧框架（上表之外）：

- **MNN-LLM**：MNN 的 LLM 专用引擎，Qwen 系列端侧部署首选，有开源 MNN Chat App
- **MLC-LLM**：TVM 团队出品，Vulkan GPU 支持好，官方有 Android demo
- **MediaPipe LLM Inference**：Google 官方 API，最容易接入但只支持 Gemma 等少数模型
- **Gemini Nano / AICore**：系统级 NPU 服务（Pixel/部分三星机型），App 免费调用，国内基本不可用
- **ExecuTorch**：PyTorch 官方端侧运行时，正在起量
- **QNN / NeuroPilot**：高通/联发科 NPU 直调，性能功耗最优但工具链碎片化，每家 SoC 一套

**选型决策线：**

```
要在端侧跑什么？
├── LLM 聊天/文本生成
│   ├── 要 Qwen 系列中文模型、工程化完整 → MNN-LLM
│   └── 模型选择自由度最大、生态最全   → llama.cpp
├── 视觉模型（检测/分类/分割）
│   ├── 追求包体最小、CPU 性能极致     → NCNN
│   ├── 需要 NPU 加速                 → TFLite (NNAPI)
│   └── 训练在 PyTorch，不想折腾转换    → ONNX Runtime
└── 视觉 + LLM 都要
    └── MNN（目前唯一同时把两边做好的单一框架）
```

**一句话总结：跑 LLM 找 llama.cpp 或 MNN-LLM，跑视觉找 NCNN 或 TFLite，跨端统一找 ONNX Runtime。** 五个框架不是竞争关系，而是按"任务类型 + 模型来源 + 加速硬件"三个维度各占一块。对 NativeAI 项目，重点看 MNN-LLM 和 llama.cpp 即可。

### 推荐架构图（架构 A）

```
┌──────────┐   HTTPS/SSE    ┌──────────────┐   服务端 SDK    ┌─────────────┐
│  Android │ ─────────────> │  自建后端     │ ─────────────> │  LLM API    │
│  客户端   │ <───────────── │ (鉴权/限流/   │ <───────────── │ (Claude 等) │
└──────────┘   流式转发      │  计费/审计)   │                └─────────────┘
└──────────────┘
```

客户端只与自己的后端通信，后端持有 API Key 并负责转发（包括流式转发）。

## 二、核心概念速览

无论选哪家的模型，接入时都会遇到这四个概念：

1. **Messages API**：所有对话都通过一个 HTTP 端点完成（Claude 是 `POST /v1/messages`），请求体包含 `model`、`max_tokens`、`messages`（对话历史）。
2. **流式输出（Streaming）**：模型逐 token 生成，服务端通过 **SSE（Server-Sent Events）** 推送增量。聊天界面"打字机效果"就靠它。**长输出必须用流式**，否则会撞 HTTP 超时。
3. **上下文管理**：API 无状态，客户端/后端负责维护对话历史并随每次请求回传。历史过长需要截断或压缩（服务端 compaction）。
4. **工具调用（Tool Use / Function Calling）**：模型返回结构化的"调用请求"，由客户端/后端执行后再把结果回传，循环直到模型给出最终答复。

## 三、客户端实现（Kotlin）

### 3.1 后端代理模式（推荐）

客户端用 OkHttp/Retrofit 与自己的后端通信，处理 SSE 流。后端接口设计成与 LLM API 形状相近，可以少写一层转换。

**依赖（libs.versions.toml + build.gradle.kts）：**

```kotlin
// app/build.gradle.kts
dependencies {
    implementation("com.squareup.okhttp3:okhttp:4.12.0")
    implementation("com.squareup.okhttp3:okhttp-sse:4.12.0")
}
```

**流式请求与 SSE 解析：**

```kotlin
class ChatRepository(private val client: OkHttpClient = OkHttpClient()) {

    /**
     * 流式对话。onDelta 每收到一段增量文本就回调（主线程消费时自行切换线程）。
     */
    fun streamChat(
        question: String,
        history: List<ChatMessage>,
        onDelta: (String) -> Unit,
        onError: (Throwable) -> Unit,
    ): Call {
        val body = buildJsonObject {
            put("messages", buildJsonArray {
                history.forEach { msg ->
                    add(buildJsonObject {
                        put("role", msg.role)
                        put("content", msg.content)
                    })
                }
                add(buildJsonObject {
                    put("role", "user")
                    put("content", question)
                })
            })
        }.toString()

        val request = Request.Builder()
            .url("https://api.your-backend.com/v1/chat")  // 自己的后端
            .post(body.toRequestBody("application/json".toMediaType()))
            .build()

        val call = client.newCall(request)
        call.enqueue(object : Callback {
            override fun onFailure(call: Call, e: IOException) = onError(e)

            override fun onResponse(call: Call, response: Response) {
                response.use { resp ->
                    if (!resp.isSuccessful) {
                        onError(IOException("HTTP ${resp.code}"))
                        return
                    }
                    val source = resp.body!!.source()
                    try {
                        // 解析 SSE：每帧 "data: {...}\n\n"
                        while (!source.exhausted()) {
                            val line = source.readUtf8Line() ?: break
                            if (!line.startsWith("data:")) continue
                            val payload = line.removePrefix("data:").trim()
                            if (payload == "[DONE]") break
                            val delta = parseDelta(payload)  // 按后端协议取增量文本
                            if (delta != null) onDelta(delta)
                        }
                    } catch (e: IOException) {
                        // 用户主动取消（call.cancel()）会走到这里，静默即可
                        if (!call.isCanceled()) onError(e)
                    }
                }
            }
        })
        return call  // 返回 Call 便于界面销毁时 call.cancel()
    }
}
```

要点：
- **返回 `Call`**：Activity/Fragment 销毁时调用 `call.cancel()`，避免泄漏和后台浪费。
- **SSE 帧格式**：每条消息以 `data: ` 开头、空行分隔；后端转发 Claude SSE 时通常是 `content_block_delta` 事件携带增量文本。
- **UI 层**：`onDelta` 回调里用 `MutableStateFlow<String>` 累积文本，Compose 直接 `collectAsStateWithLifecycle()` 渲染。

### 3.2 客户端直连模式（仅开发调试用）

Anthropic 提供 JVM SDK（OkHttp 实现），可在 Android 上直接调用：

```kotlin
// app/build.gradle.kts
dependencies {
    implementation("com.anthropic:anthropic-java:2.34.0")
}
```

**非流式调用：**

```kotlin
import com.anthropic.client.okhttp.AnthropicOkHttpClient
import com.anthropic.models.messages.MessageCreateParams

val client = AnthropicOkHttpClient.builder()
    .apiKey("sk-ant-...")   // ⚠️ 仅限调试：正式产品严禁把 Key 打进 APK
    .build()

val params = MessageCreateParams.builder()
    .model("claude-opus-5-5")
    .maxTokens(16000L)
    .addUserMessage("用一句话解释什么是 edge-to-edge")
    .build()

val response = client.messages().create(params)
val text = response.content().joinToString("") { block ->
    block.text().map { it.text() }.orElse("")
}
```

**流式调用：**

```kotlin
import com.anthropic.core.http.StreamResponse
import com.anthropic.models.messages.RawMessageStreamEvent

val streamingParams = MessageCreateParams.builder()
    .model("claude-opus-5-5")
    .maxTokens(64000L)   // 大 max_tokens 必须配流式，避免 HTTP 超时
    .addUserMessage("写一首关于秋天的俳句")
    .build()

client.messages().createStreaming(streamingParams).use { streamResponse ->
    streamResponse.stream()
        .flatMap { event -> event.contentBlockDelta().stream() }
        .flatMap { deltaEvent -> deltaEvent.delta().text().stream() }
        .forEach { textDelta -> print(textDelta.text()) }  // 逐 token 增量
}
```

> **注意**：SDK 的网络调用是同步的，Android 上要放在协程 `Dispatchers.IO` 或线程池里执行。

## 四、请求参数要点

| 参数 | 建议 |
|------|------|
| `model` | 默认 `claude-opus-5-5`；高并发/低成本路由可按需选更低档位（由后端决定，客户端不感知） |
| `max_tokens` | 非流式默认 ~16000；流式默认 ~64000；分类等短任务可降到 ~256。**不要给小了**——撞上限会截断在半句话上 |
| `thinking` | 新模型用自适应思考 `{type: "adaptive"}`（或不传），由模型自行决定思考深度 |
| `effort` | 在 `output_config` 内设置（`low`/`medium`/`high`/`xhigh`/`max`），控制思考深度与 token 花费的平衡。注意 Claude Opus 5.5 默认是 `medium`，建议显式设置 |
| `fallbacks` | 写 `claude-opus-5-5` 等新模型的服务端代码时，建议默认带上服务端 fallback 参数（beta），拒绝回答时自动降级到备用模型，避免整次请求作废 |

## 五、会话与上下文管理

1. **历史回传**：每次请求把完整对话历史放进 `messages`。历史中的 `tool_use`/`tool_result` 等内容块要**原样回传**，不能只提取文本。
2. **上下文窗口**：Claude 当前模型 1M token，但历史越长费用越高、延迟越大。策略：
   - 聊天类：保留最近 N 轮 + 一份系统提示词
   - 长任务：启用服务端 compaction（beta），接近阈值时自动摘要早期上下文
3. **Token 计数**：调用 `messages.count_tokens` 可以在发送前预估请求大小，用于决定何时截断。
4. **提示词缓存（Prompt Caching）**：把固定的系统提示词、工具定义放在请求前部并加 `cache_control` 断点，重复对话的输入成本可大幅下降（缓存读取价格约为正常输入的 1/10~1/20）。验证方式：检查响应里 `usage.cache_read_input_tokens` 是否大于 0。

## 六、错误处理

按"可重试 / 不可重试"分类处理，不要只 catch 一个宽泛异常：

| 类型 | HTTP 码 | 处理 |
|------|---------|------|
| 限流 `RateLimitError` | 429 | 按 `retry-after` 头等待后重试，建议指数退避 |
| 服务端错误 | 5xx | 自动重试（SDK 默认重试 2 次 408/429/5xx） |
| 参数错误 | 400 | **不重试**，记日志排查 |
| 模型不存在 | 404 | **不重试**，检查 model id |
| 网络错误 | - | 重试；流式中途断开要考虑断点续传或整体重发 |
| 拒绝回答 `stop_reason: "refusal"` | 200 | 检查 `stop_details.category`，走产品侧的兜底文案；服务端配 fallbacks 可自动降级 |

客户端展示层面：区分"网络失败可重试"、"内容被拒绝"、"服务繁忙"，给用户明确的操作出口。

## 七、安全清单

- [ ] **API Key 绝不进客户端**：反编译 APK 可直接读出字符串常量；`BuildConfig` 字段同理不安全
- [ ] 后端代理层做**用户鉴权 + 每用户限流 + 用量计费**，防止接口被人刷
- [ ] 用户输入与模型输出都要过**内容安全策略**（提示词注入、敏感内容）
- [ ] 明示"内容由 AI 生成"（多数应用商店上架要求）
- [ ] 不把用户隐私数据原样发给模型，先脱敏
- [ ] 流量全链路 HTTPS；后端校验客户端版本，可强制升级有漏洞的旧版本
- [ ] **Android 16+（targetSdk 36+）访问局域网设备（如调试时连电脑 `10.0.2.2` / 局域网 IP）必须持有本地网络运行时权限**，否则连接被系统静默拦截（表现为连接超时而非拒绝）：
  - API 33~36：`NEARBY_WIFI_DEVICES`（声明时加 `neverForLocation` 标志）
  - API 37+：`ACCESS_LOCAL_NETWORK`（专用权限）
  - 授权后需（重新）启动 App 进程，netd 的按 UID 防火墙规则才会刷新生效
  - adb 快速授权：`adb shell pm grant <包名> android.permission.ACCESS_LOCAL_NETWORK`

## 八、成本优化速查

1. **提示词缓存**（免费收益，优先做）：稳定内容放前部 + `cache_control`
2. **模型分级**：路由层按任务复杂度分流——简单分类/改写给低档模型，复杂推理用旗舰模型
3. **effort 调优**：同一模型降低 effort 往往比换小模型更划算（且不破坏缓存命名空间——缓存按模型隔离）
4. **按"完成任务"计成本**，不按"单次请求"：便宜但需要多轮重试的路由并不便宜
5. **批量处理**：非实时任务用 Batch API，5 折
